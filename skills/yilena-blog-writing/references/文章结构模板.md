# 文章结构模板

这些是从原文提取的结构动作，不是必须逐节填写的目录。先确定本文要回答什么，再选一套；专题短就缩短，内容复杂才增加层次。篇幅由当前任务和所选原文校准，不按混合样本均值强行配额。

## 1. 教程：提纲陪学与连贯机制

### 提纲式陪学

适合已有基础、需要系统查阅的技术主题。校准 C027、C030—C041、C043—C045，具体节奏仍有差异。

> 简短定位/定义 → 列出核心组成 → 逐个问“做什么、怎么执行、为什么” → 代码/运行输出/对照 → 风险、常混淆点 → 最后一个知识点或适用判断。

一个局部可这样组织：问题标题 → 一句可理解的定义 → 沿一次动作解释 → 展示例子 → 指出条件。不是每个小节都要完整重复此顺序。

开头不必讲时代趋势，可先说某个机制解决的直接问题。问题标题可以很短，但修复旧稿时补回迁移中丢失的主语，不复刻“什么是？”这样的残缺标题。

结尾可停在最后一项，用一两句范围判断收住。C034 的部分专题很短，不需要补“价值、意义、未来展望”。

### 连贯机制解释

适合需要把执行过程讲透的主题，校准 C028、C029，辅以 C043、C045 的相关段落。

> 具体工作负载 → 朴素机制为何吃力 → 建立直觉 → 内部执行过程 → 代码/图表复现 → 跨方案对照 → 资源、团队与使用边界。

每段保留一个完整因果关系；机制之间有承接才换段。类比可贯穿，但必须映射到具体组件，不用类比代替事实。不能只因文章日期较新就强制改成长段。

### 三种专题变体

- **追一条路径**：组件地图 → 一次请求/消息依次经过什么 → 留下哪些状态 → 如何失败或确认。参照 C032、C037、C039、C041、C045。
- **同维度选型**：明确共同任务 → 固定比较维度 → 对相同负载解释差异 → 给条件化建议。参照 C025、C029、C036。不要一边只列优点、一边只列缺点。
- **小范围用法**：读者已经知道基础 → 本次参数/边界 → 最小例子 → 常见失效点。参照 C042，不补完整入门史。

## 2. 深度解析：从症状到系统边界

校准 C008、C012—C016、C048—C049。

> 真实任务中的落差 → 澄清概念及相邻概念 → 核心组成与职责 → 执行机制/信息流 → 方案演进或横向比较 → 生产中的成本、恢复和治理 → 回收本篇判断。

开头可以提出一个朴素理解，随后用任务困难说明它为何不完整。纠偏必须产生新的区分，不能只是“不是 X 而是更高级的 X”。

正文常用“直觉→机制→工程后果”：例如定义状态之后说明谁读写、何时更新、失败后如何恢复。图示承接关系，表格压缩同维度差异；二者不应替代原因解释。

历史演进用于说明某种约束何时出现，不写成必然升级路线。结尾允许方法论回收，但只能回收前文已经讨论的机制和代价。没有研究资料时不硬写“行业公认”“所有团队”。

## 3. 方案复盘：约束推动变化

校准 C001—C002、C018—C020、C022、C050、C053、C058。

> 场景/数据量/硬要求 → 直观候选或旧实现 → 运行观察/成本计算 → 暴露瓶颈 → 针对性调整 → 引入的新代价 → 最终方案与关键代码 → 结果及适用边界。

局部循环是“提出→检验→追问→修改”。C001 将注意力从线程数转向请求次数；C022 的令牌职责因用户体验和状态要求逐步拆开；C050 按当前店铺和更新时效缩小问题。

若材料没有旧版和实测，把结构改成：约束→候选 A/B→按同一标准比较→推荐实现→待验证指标。不得补造“初版跑了多少秒”“线上崩过一次”来凑复盘感。

开头先给影响设计的约束，不把所有中间件名单排上来。结果用用户提供的口径；估算请求数、观察耗时、因果推断分开。后文如有局限，允许承认当前方案不完美。

## 4. 直接排障：对照条件就是引子

校准 C004、C005、C007、C009、C010、C046、C059。

> 环境与操作 → 现象/对照 → 决定性的日志或差异 → 判断及置信边界 → 最小修改 → 观察到的恢复/待验证 → 仅相关的补充分支。

常见开头不是悬念，而是具体矛盾：配置看似相同却失效、工具正常而前端失败、没有配置认证却出现认证页面。保留读者用于比对的环境信息。

有两种解法时说明选择条件；如果只知道某操作有效，就如 C046 那样保留机制未知，不把经验修法伪装成所有问题的统一根因。后续发现新分支，可追加日期更新与触发条件。

结束处不必升华：已经观察恢复就写恢复，没观察就明确写验证方法。本文不决定具体排障结论正确与否。

## 5. 项目记录：按功能和运行顺序拆开

校准 C003、C006、C054—C056。

> 成品效果/用户可做什么 → 需求与范围 → 技术栈或对象职责 → 功能逐项展开 → 关键代码 → 沿执行顺序解说 → 局限与后续。

作品展示型 C006 以截图和功能地图为主；代码讲解型 C003、C054—C056 以对象、事件、数据流为主。不要混成“40 张截图＋全量源码＋完整入门”作为默认稿型。

每项功能先说为什么需要它，再介绍对应新知识；代码后的“首先、接着、最后”对应真实执行步骤。客户端/服务端场景可沿一条消息分别解释两端，避免按文件名随机串读。

结尾可以写具体遗留与学习收获，不必模仿旧平台的求赞语和自谦口头禅。

## 6. 工具介绍：让效果受条件约束

直接样本 C021 仅一篇，借 C006 的功能展示、C027 的原理/使用说明补充校准。

> 想改善什么 → 观察到的效果与设备条件 → 哪些机制起作用 → 安装/运行/参数 → 日志或验证入口 → 限制。

标题中的数字不能变成所有用户的保证。写作材料没有测量条件时，标题改用功能和使用场景，不造大数字吸引点击。

## 7. 个人随笔：让时间带着感受往前走

唯一直接样本 C052。不能由一篇推出覆盖旅行、书评或生活全部题材的模板。

> 一个时间节点及当时处境 → 做决定 → 期待变化 → 结果落差 → 当时如何解释它 → 现在仍留下什么。

短段、独句出现在事件转折和情绪落点，不要求每句话单独成段。具体事件先于抽象感悟。可以自勉，也可以保留“知道道理但还没消化”的矛盾。

不替用户写不存在的学校、面试、工作或心态。材料只含事件没有感受时，可先写克制的事实叙事，必要处询问，而不是自动补满受挫与成长。

## 标题与章节的选择

语料标题可归为对象＋学习承诺、现象＋解法、场景＋方案、变化数字＋机制、概念＋解释范围，以及具体个人事件。新题目选择匹配内容的一种；“一文讲透”“轻松学习”“大杀器”等原有承诺不是每篇都要沿用。

只有真实数字才使用数字变化标题；只有覆盖了对应范围才承诺全景。章节标题可以用中文数字和括号，也可以用清楚的短语，目标是让读者找到问题位置，不复制手工目录和 `#t0` 锚点。
